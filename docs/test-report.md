# ohlc 第一版基准性能测试报告

版本：1.0\
软件基准：0.1.0-beta.1\
四库对照规模：10,000 只股票 × 8,580 根分钟线 = 85,800,000 条\
测量日期：2026-09-27，对照 17:32–18:29，空间复核至 18:31；退市专项 19:17–19:34（UTC+8）\
状态：测量完成；退市专项 15 场景通过；InfluxDB 16 客户端并发触及 32 GiB 上限后 OOM

本报告记录第一版基准的实际测量，比较 ohlc、MySQL、ClickHouse 与 InfluxDB 2 OSS。
四库各写入相同的 8,580 万条行情，并通过完整性检查。全部测量采用客户端—服务器模式。
第 8 节另测退市、分散空槽及新增证券，使用同一产品版本；其数据分布与查询窗口单独定义。

**ohlc 的批量导入优势显著，但查询性能并非全面领先。** 行情批量提交耗时 19.33 秒，
约 443.8 万行/秒；计入首次证券注册及检查点后为 37.60 秒。预热后 240 行范围与横截面
的中位延迟分别为 0.257 和 4.313 毫秒。MySQL 在长区间中位延迟、16 客户端吞吐及
重开后的横截面读取上更好；InfluxDB 使用原生压缩后的磁盘占用最小。

这些结论只适用于下述数据、索引、缓存、协议与资源配置，不能直接推广到所有数据库用途。

## 1. 测试契约

- 主比较采用同机回环 TCP、持久连接、实际返回全部七字段；不使用 COUNT 或仅定位作为查询耗时。
- 单股范围覆盖 1、240、2,048、8,580 条；横截面返回 10,000 条。
- 统一按成功前的落盘确认配置写入，逐项记录产品语义差异；不将异步接收当作持久完成。
- 允许各数据库采用适合两类查询的原生索引和压缩，完整计入其数据、索引及副本空间。
- 区分批量提交确认、整理/检查点完成、热读取、重开后的首次读取和并发吞吐。
- 校验计数、全部字段校验和及查询结果；固定随机种子，保存每条原始计时。
- 核心源码保持基准版本；原始证据保留实际执行的工具源码及指纹，计量工具的兼容修正单独注明。

## 2. 数据集与比较边界

正式数据只有一张分钟表。10,000 个证券各有 8,580 条完整行情，共 85,800,000 行、
600,600,000 个整数值；七字段有效载荷为 2,745,600,000 B（约 2.557 GiB）。
不包含行情缺失、覆盖更新、删除、多表竞争或自动聚合。

时间轴从 `2026-08-31 13:30:00 UTC` 开始，包含 22 个合成交易时段，每段 390 分钟；
每五个时段跳过两个自然日。它是可重复的测试日历，不是真实交易日历，也不是历史行情。
输入按时间优先、同一分钟证券编号递增排列，每批 100,000 行，共 858 批。
价格、成交量、成交额由固定整数公式和 SplitMix64 生成，复权因子固定为 1,000,000。
这些特征会影响压缩率，因此空间结果只代表本合成数据。

MySQL 和 ClickHouse 使用相同的 `UInt32 ticker + UInt32 time_key` 逻辑键；
ohlc 注册证券字典后使用稳定编号，InfluxDB 使用五位定宽字符串 ticker 标签和原生时间戳。
所有查询返回一个变化的键与全部七字段；输入中已给定的另一维键不重复传回。
各库保留自身原生的数据类型、索引、压缩及协议开销。

主比较衡量**客户端发出请求至收齐、解码结果的端到端延迟**。
查询字符串生成、协议处理和数据解码在计时内；建立持久连接、字典/表句柄准备、
测试进程之间的控制通信和结果正确性核验在单次延迟计时外。
并发吞吐的完整测试窗口包含结果核验成本。没有用嵌入式库耗时冒充客户端—服务器耗时。

## 3. 环境与配置

四个数据库在同一台 Linux 服务器依次运行，测试数据位于 `/ssd02` 的独立目录。
服务器已有的 MySQL 实例不参与本次测试；对照实例绑定独立的回环端口。
正式测试期间不修改 ohlc 内核、服务或客户端实现。

| 项目 | 配置 |
|---|---|
| CPU | 双路 Intel Xeon Platinum 8260，2.40 GHz，48 物理核 / 96 逻辑 CPU |
| 服务 CPU | 同一 NUMA 节点的 CPU 0–15，16 个物理核 |
| 客户端 CPU | 同一 NUMA 节点的 CPU 16–23，8 个物理核 |
| 内存 | 约 125 GiB；每个被测服务的 cgroup 上限 32 GiB，禁止该组交换 |
| 测试盘 | KIOXIA EXCERIA PLUS G2 1 TB NVMe，XFS，`/ssd02` |
| 平台 | RHEL 9.4 x86-64，内核 5.14.0-729.el9；GCC 11.5.0 |
| 连接 | 本机回环 TCP、持久连接、无 TLS、HTTP 响应不压缩 |
| ohlc | 0.1.0-beta.1，Release 构建，默认 16 × 8 布局，无压缩；引擎预算 1 GiB，应用缓存 64 MiB，默认同步读调度 |
| MySQL | 8.0.46，InnoDB，16 GiB buffer pool，2 GiB redo，O_DIRECT，doublewrite 开启 |
| ClickHouse | 25.8.31.9 LTS，MergeTree，查询线程上限 16，服务内存目标 16 GiB；默认原生压缩 |
| InfluxDB | 2.9.1 OSS，TSM / TSI；每分片写缓存上限 1 GiB，64 MiB 触发快照，Go 并行度 16 |

32 GiB 是统一的服务组上限，不代表四者实际占用相同。MySQL 的 buffer pool、
ohlc 的分配器预算与内核页缓存不是同一种指标；报告将实际进程 RSS 与数据库文件占用分开列出。
本轮数据可能被整机内存容纳，预热查询不能代表超过内存的数据集。

### 3.1 两个查询方向的访问路径

| 数据库 | 证券范围 | 时间横截面 | 额外空间 |
|---|---|---|---|
| ohlc | 常驻时间映射、二维块、计算寻址 | 同一批二维块中的固定列 | 完整块元数据、共享目录、检查点和 WAL |
| MySQL | 主键 `(ticker,time_key)` | 覆盖二级索引 `(time_key,ticker,七字段)` | 完整计入覆盖索引 |
| ClickHouse | `ORDER BY (ticker,time_key)` | 完整投影 `ORDER BY (time_key,ticker)` | 完整计入投影；两种顺序均使用原生压缩 |
| InfluxDB | ticker 标签过滤 + 时间范围 | 指定时间访问各证券序列 | 原生标签索引和各字段时间序列 |

ClickHouse 的 `index_granularity=256`、`index_granularity_bytes=0`，关闭查询结果缓存和
查询条件缓存。通过保存的查询计划核对投影选择；MySQL 保存 EXPLAIN 核对覆盖索引。
使用 C 公共驱动：ohlc 二进制协议、MySQL 预编译语句二进制结果、ClickHouse HTTP RowBinary，
InfluxDB 的 InfluxQL `/query` 返回 CSV。InfluxQL 的兼容 API 和 CSV 返回方式见
[官方查询文档](https://docs.influxdata.com/influxdb/v2/query-data/execute-queries/influx-api/)。
协议与解码差异是本轮端到端结果的一部分，不能据此单独推断存储内核快多少。

### 3.2 持久性与整理

- ohlc：写入成功前同步 WAL；导入后显式完成检查点。
- MySQL：`innodb_flush_log_at_trx_commit=1`，开启 doublewrite；单机比较关闭 binlog，
  导入后等待脏页刷完。提交刷盘语义见 [InnoDB 官方参数说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-parameters.html#sysvar_innodb_flush_log_at_trx_commit)。
- ClickHouse：`async_insert=0`、`fsync_after_insert=1`、`fsync_part_directory=1`；导入后执行
  `OPTIMIZE FINAL`。同步参数见 [MergeTree 官方说明](https://clickhouse.com/docs/reference/settings/merge-tree-settings/fsync)。
- InfluxDB：`storage-wal-fsync-delay=0s`；冷写快照阈值 5 秒、全量整理冷写阈值 15 秒，
  等待引擎文件稳定 25 秒后进入查询阶段。WAL 同步参数见
  [InfluxDB 官方参数说明](https://docs.influxdata.com/influxdb/v2/reference/config-options/#storage-wal-fsync-delay)。

这使对照均使用成功前的持久写入配置，但没有把四者的事务、跨分片原子性、复制和恢复能力
视为相同。整理等待时间单独列出。本轮未做真实断电，也未验证 SSD 内部掉电保护。

## 4. 查询与计量方法

| 项目 | 负载及采样 |
|---|---|
| 单股范围 | 随机证券；返回 1、240、2,048、8,580 行，按真实时间排序 |
| 分钟横截面 | 随机已存在分钟，返回全部 10,000 只证券 |
| 预热后随机查询 | 每轮每类先做 16 次预热，再计 40 次；3 轮，每类 120 个计时样本 |
| 并发读取 | 1、4、8、16 个客户端；各执行 3 轮，每轮 15 秒；240 行范围与横截面交替 |
| 重开后的首个查询 | 每类 5 次；240 行、8,580 行范围与横截面各自测量 |
| 计时 | C17 `CLOCK_MONOTONIC`；分位数用最近秩，跨轮保留原始样本 |
| 正确性 | 每次查询逐行核对键、数量及七字段；范围必须有序，横截面证券不可重复 |

预热后随机查询的目标在各轮继续变化，不声称每个请求均命中应用缓存。
导入后的完整性校验也会影响缓存状态。并发吞吐为闭环客户端实测，不表示固定到达率下的
服务能力；需与返回行数、并发数和延迟一起阅读。

首次查询测试先正常停机，只对本次数据库的文件执行 `POSIX_FADV_DONTNEED`，以 `mincore`
记录清除前后的驻留页，再重开服务并立即执行一个业务查询。不清空整台服务器页缓存。
启动恢复会重新读取索引和元数据，因此这是“清理本库页缓存并重开后的首个查询”，
不是绝对无缓存的裸盘随机 I/O。样本数只有 5，报告中只比较中位数及范围，不推断尾延迟。

MySQL 保持默认 `innodb_io_capacity=200`、`innodb_io_capacity_max=2000`，
整理阶段可能受这个刷盘预算影响；该配置的结果不能代表所有 NVMe 调优配置。

导入阶段只有一次正式全量运行；没有多次导入的统计置信区间。
读取、验证、整理和数据生成的耗时均不混入批量提交确认计时。
结果中的 GB 使用 10^9 B，GiB 使用 2^30 B；磁盘同时记录逻辑长度与实际分配量。

### 5.5 磁盘与内存

磁盘是测量时数据库目录的全部文件，去重硬链接，排除原始输入、测试日志和程序二进制。
RSS 是服务组全部进程 RSS 合计的采样峰值，共享页可能重复计入；
cgroup 还可能包含已计账的文件页缓存等内核内存，不能与 RSS 相加。采样间隔为 0.5 秒。

| 数据库 | 文件逻辑长度 GB | 实际分配 GB | 观测 RSS 峰值 MiB | 观测 cgroup 峰值 GiB |
|---|---:|---:|---:|---:|
| ohlc | 4.227 | 4.228 | 222.8 | 4.984 |
| MySQL | 12.810 | 12.810 | 10,974.7 | 12.708 |
| ClickHouse（旧分片清理后） | 4.362 | 4.362 | 991.9 | 20.286 |
| InfluxDB 2 | 1.559 | 1.526 | 32,769.3 | 32.000 |

ohlc 的数据卷约 3.976 GB、块元数据约 31.06 MB、索引约 3.88 MB、保留 WAL 约 216.01 MB。
数据卷高于约 2.747 GB 的当前二维块有效布局，原因是检查点追加了旧镜像；本版不回收这些数据 extent。
32 B/行是行载荷，不能直接当作运行目录空间。

ClickHouse 的活跃 part 共 4.362 GB，其中已包含 2.507 GB 的时间投影，不能再把投影重复相加。
主测量结束时，目录另有约 16.788 GB 非活跃旧 part 等待清理，实际分配量为 21.316 GB。
全部性能查询结束后才将 `old_parts_lifetime` 调为 0，约 2.06 秒后确认非活跃 part 为 0，
目录实际分配量为 4,362,215,424 B。上表采用此清理后的磁盘数值，内存仍是正式运行时的峰值；
所有性能查询均使用清理前的原配置。没有把临时旧文件计成永久容量。

InfluxDB 的实际分配量为 1,526,489,088 B，是本合成数据下最小的目录；
逻辑长度与分配量的差异包含稀疏文件。其内存峰值来自发生 OOM 的正式阶段，
磁盘取自恢复校验及首次读取完成后。四库均未观察到交换使用；InfluxDB 记录 1 次 OOM kill，
其他三库为 0。RSS 与 cgroup 来自不同计量口径及采样时刻，不要求数值逐字节相等。

以上为指定配置的观察值。ohlc 应用缓存为 64 MiB，而 MySQL buffer pool 为 16 GiB；
它们不代表相同的缓存命中条件。本轮没有测量逐项等内存预算调优后的最优值。

| ohlc | 逐行核对全部 85,800,000 条的键及七字段 | 840 次，全部正确 | 396,762 |
| MySQL | 总行数及七字段整数求和全部匹配 | 840 次，全部正确 | 427,507 |

每个完整查询都逐行核对数量、键与七字段。上表并发计数只包含成功完成的轮次，
InfluxDB 第二个 16 并发轮次中断前的请求不进入统计。每库还完成 15 次重开后首次查询，

InfluxDB 被 OOM 终止后重新打开同一数据目录，再次验证 85,800,000 条与七字段求和均一致，
随后才补齐首次查询和磁盘测量。它证明这次进程被终止后的恢复检查通过，不等同于真实断电验证。
原始失败日志与补测记录均保留，未覆盖或删除失败轮次。

MySQL 的横截面 EXPLAIN 显示使用 `by_time` 且为 `Using index`。
ClickHouse 正式留存计划显示使用 `by_time` 投影，首分钟选择 40 / 335,157 个 granule。
结束后的辅助诊断又检查了三个不同分钟，实际读取 10,048–10,240 行，返回 10,000 行；
诊断样本未混入正式延迟。该结果排除了所检样本全表扫描的解释，尚未定位其查询耗时的具体组成。

## 7. 结论与适用范围

1. **批量写入是 ohlc 最清楚的优势。** 行情批量提交吞吐分别是本配置 MySQL、ClickHouse、
   InfluxDB 的 22.92、5.17、60.81 倍。计入证券注册与整理后三项合计的耗时比为
   18.45、4.10、32.59；这些数字不包含建库和正确性校验，也没有多次导入的置信区间。
2. **ohlc 对小范围读取的响应快，较 MySQL 的优势随结果增大而缩小。** 240 行预热查询
   为 0.257 对 0.400 毫秒；横截面为 4.313 对 5.054 毫秒。2,048 和 8,580 行的中位延迟
   则由 MySQL 略微领先，ohlc 的本轮 p95 / p99 更低。
3. **高并发与重开后的横截面仍有明确优化空间。** 16 客户端时，MySQL 吞吐是 ohlc 的
   1.39 倍；重开后横截面的中位延迟为 8.38 对 52.16 毫秒。二维布局的计算定位快，
   并不保证整个查询的数据读取和结果传输都更快；本报告不据此推断未经剖析的具体瓶颈。
4. **磁盘结果体现不同取舍。** ohlc 4.23 GB，ClickHouse 清理后 4.36 GB，两者接近；
   MySQL 12.81 GB，InfluxDB 1.53 GB。不能把 ohlc 的低进程 RSS 解释成只需要该数值的总内存，
   也不能把不压缩行存描述为所有场景下最省空间。
5. **InfluxDB 的失败属于本轮指定配置。** 16 并发在 32 GiB 上限下未通过；这不是对
   InfluxDB 经过其他内存、查询并发或数据组织配置调优后能力的上界判断。

第 1–7 节的四库对照只覆盖稠密单表、合成分钟行情、全字段读取与固定写入顺序。
退市与新增证券的专项测试见第 8 节。四库对照没有覆盖 20 年数据、
超过机器内存的数据集、稀疏历史补录、多表竞争、边写边查、长时间稳定性、跨主机 TLS、
复制容灾或 Linux ARM64。当前结果足以建立这份代码的可复核基准，不能替代这些独立验收。

## 8. 退市、空槽与新增证券专项测试

### 8.1 目的与负载

本节单独测量证券停止写入之后的空间及读取成本，沿用同一冻结的 `0.1.0-beta.1`
产品源码与 Linux x86-64 二进制，不改变存储布局或产品代码，也不重复四库对照。
硬件与第 3 节相同，使用 `/ssd02` 上独立临时数据库；32 GiB 服务组上限、1 GiB 引擎预算、
64 MiB 应用缓存、默认串行读取调度与回环 TCP 保持不变。证券仍通过当前显式注册接口添加。

每个场景从 10,000 只证券开始，共观察 8,580 个合成分钟时间点。前 4,096 个时间点具有相同的
40,960,000 条历史行情；先建立、完整校验并关闭这份共享前缀，再逐文件复制给各场景，
核对 SHA-256 并刷盘后才打开。复制耗时不计入行情写入耗时。后续 4,484 个时间点的记录
按证券存续区间生成，七字段公式与第 2 节一致。分钟序号仅供测试生成器使用，实际接口仍传真实时间。

设置 15 个正式场景：无退市 1 个；单次退市 6 个；退市后等量补入新证券 6 个；
反复退市并补足活跃数 2 个。整组退市选择连续的完整 16 证券组，分散退市从仍活跃的编号中
均匀选取。为让单股查询始终读取同一只证券，原始编号最后一个 16 证券组始终存续，
占最初证券数的 0.16%；这不是无条件均匀随机抽样。

| 名义退市比例 | 单次退市数 | 实际比例 | 不补入时最终活跃数 |
|---:|---:|---:|---:|
| 10% | 992 | 9.92% | 9,008 |
| 50% | 4,992 | 49.92% | 5,008 |
| 90% | 8,992 | 89.92% | 1,008 |

取整到 16 的倍数，使整组与分散场景退市数一致。单次事件发生在序号 4,096；
九轮更替在 4,096、4,608、5,120、5,632、6,144、6,656、7,168、7,680、8,192 各退市
4,992 只并补入 4,992 只，最终累计注册 54,928 只、活跃仍为 10,000 只。
新证券取得递增的新编号，不占用旧证券位置。所有比例和更替频率均是合成压力条件，
不代表实际市场的日退市率，也不能直接外推 20 年增长。

### 8.2 校验与计量口径

每个场景完成写入和检查点后正常重开，逐条校验后续全部 4,484 个横截面的键、七字段、
数量及顺序。共享前缀在建种子库时全量校验，复制前后的文件哈希必须一致；
各场景写入之后再抽检历史横截面与退市证券历史，不宣称每个场景都重新全扫此前 4,096 个时间点。
生命周期边界另外检查退市后零记录、退市前 240 条仍在，以及新增证券首次写入前零记录、
首次写入后 240 条正确。

| 读取类别 | 查询目标 | 返回行数 |
|---|---|---:|
| 近期横截面 | 最后 128 个时间点内固定随机序列 | 最终活跃证券数 |
| 历史横截面 | 序号 3,968–4,095 内固定随机序列 | 10,000 |
| 单股 240 行 | 固定存续证券编号 9,999；起点在后续区间随机选取 | 240 |
| 单股 2,048 行 | 同一证券；起点在后续区间随机选取 | 2,048 |

各场景使用完全相同的查询目标。预热测试每类 3 轮，每轮先 16 次预热、后 40 次计时，
每类 120 个正式样本；计时覆盖请求至完整接收、解码，不包含逐行校验和请求前后的统计查询。
预热仅描述方法，不表示所有访问均命中应用缓存。此处证券选择和时间窗口与第 4 节不同，
必须使用本节新测的“无退市”对照，不能把延迟变化解释为产品优化。

重开首读每类 3 次：停止服务、仅清理本库文件页缓存并核对驻留页、重新启动，
记录首个业务查询。启动读取元数据的成本单列，不包含在首读延迟中；3 个样本只报告中位数与范围，
不推断尾延迟。`read_bytes` 是引擎数据读取路径请求的字节数，不是 NVMe 设备实际读取量；
`read_bytes / (返回行数 × 32 B)` 为行载荷读取放大。进程 RSS 与引擎分配量分开报告。

### 8.3 空间占用

不补入新证券的 10%、50%、90% 场景，整组与分散的总行数分别都为
81,351,872、63,415,872、45,479,872。其他场景均为 85,800,000 条。
单次补入后累计注册数分别为 10,992、14,992、18,992；九轮更替为 54,928。

“当前块”按存续区间与 16 × 8 布局计算，包含空槽，排除卷头、元数据、目录、旧镜像和 WAL；
“后续填充率”只计算序号 4,096 之后的记录载荷 / 当前块载荷，末尾未满的 8 时间点块也计入。
这两个指标是确定性模型值，文件逻辑长度与实际分配量是结束后停机测得的目录快照。

单位：GB = 10^9 B。额外镜像列由数据卷逻辑长度扣除卷头及当前块模型推导，

这些结果区分出三种开销：

- **空槽损失。** 仅分散退市时，每组仍有证券写入，后续块数不随活跃证券数等比例减少。
  约 90% 分散退市后，后续填充率只有 10.07%；整组退市仍为 99.91%。
- **历史镜像及日志。** 旧行情本来就必须保留，此外检查点追加的旧镜像和保留 WAL 也占空间。
  本版不整理数据 extent；保留日志受分段与检查点边界影响，不能按剩余活跃证券比例估算。
- **文件系统预分配。** 部分文件的已分配块超过逻辑 EOF。例如正式更替过程的一次只读诊断中，
  数据卷逻辑长度为 1,617,924,096 B，已分配 3,719,364,608 B；
  两次 stat 之间长度和分配量一致，FIEMAP 显示 EOF 后有 2,101,440,512 B 未写入 extent。
  这部分不是额外行情，也不是二维块里的空槽。

测试机 XFS 未设置固定 allocsize，实测后台预分配扫描间隔为 300 秒。
XFS 文档说明动态 EOF 预分配及对干净文件未使用预分配的后台清理；
FIEMAP 的 UNWRITTEN 标志表示已分配但未写入的 extent。
因此上表实际分配列是该时刻真实占用，不能当作清理完成后的永久容量；
本轮没有为了得到更小数字而调整文件系统配置或补做整理。
参见 [XFS 文档](https://docs.kernel.org/admin-guide/xfs.html)、
[FIEMAP 文档](https://docs.kernel.org/filesystems/fiemap.html)。

九轮分散更替与整组更替始终保存相同行数，当前块模型为 5.124 对 2.747 GB，
文件逻辑长度为 6.084 对 3.417 GB。这个差异表明，在固定编号、固定分组的当前实现下，
证券生命周期分布确实会影响容量；它不能仅用“活跃股票一直是 10,000 只”来估算。

### 8.6 内存

“重开引擎分配量”在检查点后正常重开、尚未进行业务读取时取得，
包含字典、全部定位元数据、缓存分配及其他引擎对象，**不是纯索引大小**。
64 MiB 缓存容量已经包含在引擎分配中，不能再次相加。RSS 是物理驻留页，
没有触及的分配页不一定驻留，因此可以低于引擎分配量。

下面的重开 RSS 为 12 次首读之前采样的中位数；RSS / cgroup 峰值来自写入、检查点后重开、
校验及预热阶段的 0.5 秒采样。首读各次重启没有连续采样，不将它们称为全程绝对峰值。
cgroup 还包含文件页缓存等，不能与 RSS 相加。

| 仅退市·分散 90% | 10,000 | 88.74 | 30.10 | 845.05 | 2.332 |

### 8.7 验收结果与含义

正式测试于 2026-09-27 19:17:54–19:34:32（UTC+8）完成，15 个场景全部成功。
共享前缀和各场景后续区间累计逐条验证 579,255,232 条，包含相同前缀以外的跨场景重复行情；
这个数字不是一个数据库里唯一行数。另有 10,080 次预热/计时查询，其中 7,200 次正式计时，
180 次重开首读、44 次生命周期边界查询，返回键、数量和七字段均通过校验。
之前的小规模 15 场景检查同样通过，其性能数字不混入正式结果。

本轮得到的结论是：

1. **停止插入不会破坏历史数据，也不会自动生成退市后的零值记录。**
   新证券不复用旧编号，首次写入之前查询为空，正常重开后行为一致。
2. **退市分布会影响空间和近期横截面。** 完整闲置组可以跳过；
   分散退市留下的组内空槽降低填充率，新证券又使用新组，可能累积读取放大。
3. **累计注册数量不是唯一成本指标。** 九轮整组更替即使注册数增长到 54,928，
   近期首读仍接近无退市；分散场景非空组增至 1,873 后则明显变慢。
   这支持将非空组数与填充率纳入容量和性能观测，不说明扫描大量完全空目录永远没有成本。
4. **现有设计适合保留正确历史，但没有消除长期稀疏化代价。**
   后续若要优化，需针对真实生命周期分布分别评估非空组遍历和块布局；
   仅减少空目录检查不能消除仍需读取的稀疏非空块。此次只做测试，没有修改产品布局。

测试限定为单表、顺序批量写入、单读客户端、固定字段、合成生命周期及这台 Linux x86-64 主机。
没有重复并发读写、故障注入、四库对照、跨主机网络、ARM64 或真实 20 年数据测试。
这是一组可复核的压力测量，不能据此判断现实退市率下必然发生同样倍数的退步。
